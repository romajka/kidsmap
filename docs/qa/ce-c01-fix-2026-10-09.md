## 3. Первопричина и исправление

`PlaceAdminForm.__init__` проецировал canonical candidate лишь на unbound GET. Bound POST использовал live instance. При отсутствии нового файла Django FileField использует initial; initial происходил от live photo, пустого у нового draft. `publication_forms.save_form` сериализовал эту пустоту поверх сохранённого candidate.

Теперь bound форма получает `initial` и значения instance только для `photo` и `cover_photo` из `candidate_for_edit`. Проекция instance нужна для сохранённой пустоты: при следующем POST без файла cleaned None означает для FileField.save_form_data «не менять», а старая live instance иначе восстанавливает удалённое фото. Остальные initial/POST поля и поля instance остаются прежними. Django ClearableFileInput сохраняет различие no upload / clear / replacement; это подтверждено регрессиями. Версия, signed token, source/dependency checks, ACL и canonical publication не менялись.

Официальные источники сверены через Context7: [ImageField](https://docs.djangoproject.com/en/6.0/ref/forms/fields/#imagefield), [ClearableFileInput](https://docs.djangoproject.com/en/6.0/ref/forms/widgets/#clearablefileinput). Runtime FileField.clean также проверен в установленном Django6.0.2: отсутствие upload возвращает initial, явный clear возвращает False.

Проверка явного удаления выявила необходимое сопутствующее исправление: media JS искал `id_photo-clear`, тогда как Django widget создаёт `photo-clear_id`. При сохранении existing photo этот неправильный selector препятствовал явному удалению. Кнопка теперь находит checkbox по имени поля `photo-clear` внутри media section. RED браузера: unchecked/пустой multipart clear; GREEN проверяет настоящий submit clear и reload. Это тот же admin media scope, без изменения shared widget/других форм. Финальные151 серверный тест и browser прогоны выполнены после обоих исправлений.
