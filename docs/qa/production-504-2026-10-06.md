# KidsMap: восстановление после 504

Дата: 2026-10-06, Asia/Baku. Исполнитель: root этой задачи, без делегирования. Пользователь прямо поручил подключиться к production и исправить недоступность. Scope: диагностика и минимальное восстановление HTTP; это отдельная авторизация относительно предыдущего read-only UX-аудита. Пароль, env и исходные production logs не сохранены.

## 1. Состояние

kidsmap.az резолвится на указанный сервер. До исправления внешний запрос завершался timeout20s; nginx error marker aggregate:44 upstream timeouts из44 последних строк. Production repository `/opt/kidsmap`: HEAD `07abeae3`, clean. Локальный dirty WORKTREE другой версии не выкатывался.

## 2. Что работало

nginx active, web container Up8days, PostgreSQL/Redis healthy. Свободно64GB диска, память не исчерпана. Read-only pg_stat_activity: idle4, active1 (сама диагностика), waiting locks0; Redis PONG. Не обнаружена причина в DB lock или нехватке диска.

## 3. Подтверждённая причина

Два Gunicorn gthread worker по4 request threads заблокированы в чтении HTTP request headers: `gunicorn/http/unreader.py:chunk` → `message.py:read_line/parse` → `workers/gthread.py:handle`. Read-only py-spy dump обрабатывался на сервере, выведены только frame metadata, без locals/HTTP payload. В worker sockets сначала684+855 CLOSE_WAIT, позднее685+857. Третий worker ещё обслуживал часть запросов; результат intermittent timeout/200.

Docker публиковал8000 на0.0.0.0 и[::]. Nginx использует127.0.0.1:8000; публичный порт позволяет обход nginx. Зависшие запросы соответствуют slow/incomplete HTTP header pattern. Злонамеренность и источник трафика не устанавливались. Это конкретный отказ приёма HTTP до Django, а не доказательство ошибки homepage SQL.

## 4. Tech debt

Следующее отдельное release улучшение: bind Docker upstream к loopback в согласованной конфигурации вместо публичного publish. Во время инцидента container не пересоздавался, чтобы не затронуть image/env/startup checks. Текущая защита реализована scoped firewall rule.

## 5. Изменения и риски

Созданы только `/usr/local/sbin/kidsmap-protect-upstream` (0750) и `/etc/systemd/system/kidsmap-protect-upstream.service` (0644). Unit enabled под docker.service, After/Requires/PartOf docker.service. Idempotent script ограничивает внешние входящие TCP8000 через default public interface: IPv4 DOCKER-USER и INPUT, IPv6 INPUT; если IPv6 DOCKER-USER существует, добавляет правило туда. Comment: `kidsmap-protect-upstream`. Loopback upstream nginx сохраняется, SSH/80/443 правила не меняются.

Gunicorn master получил HUP, созданы3 новых worker. Два старых header-reader worker не завершились самостоятельно более80s; после проверки имени и PPid только эти2 stale PID принудительно завершены. Новые worker и master не убивались. DB/cache containers, приложение, image, env, schema и nginx configuration не изменены.

Правило DROP должно сохраняться в общей эксплуатационной конфигурации. Автозапуск enabled и ручной повтор script проверены; reboot/Docker restart для проверки здесь не выполнялись.

## 6. Cleanup / rollback

Временный диагностический binary в `/tmp` удалён после stack inspection. Не удалялись данные приложения. При необходимости rollback требует отключить новый unit и убрать только правила с comment `kidsmap-protect-upstream`; это вновь откроет прямой порт и потому не выполнялось. Rollback worker reload не нужен: текущая версия приложения сохранена.

## 7. Выполненные проверки

- Локальный upstream `/healthz` с Host и X-Forwarded-Proto:200.
- Внешние HTTPS: homepage200, /ru/200, /ru/catalog/200, /healthz200, /robots.txt200, /sitemap.xml200, admin login200.
- Повтор homepage/RU/catalog запросов прошёл; наблюдаемые ответы примерно1-5s, performance tuning не выполнялся.
- Прямой IPv4 TCP8000 снаружи: connection timeout вместо доступа к Gunicorn.
- IPv4/IPv6 rule existence:iptables/ip6tables -C PASS; service active/enabled; повтор script не создаёт дубликат DOCKER-USER rule.
- После завершения старых reader: master +3 workers, CLOSE_WAIT0 у всех.
- Rendered browser production homepage: корректные title/H1, нет502/504, console errors0 (одно предупреждение на первом открытии).
- Production Git HEAD прежний, clean; PostgreSQL/Redis healthy.

NOT RUN: reboot, Docker restart, внешний IPv6 probe, полномасштабный slow-header/load тест, full application suite, security audit и независимая проверка. Test suite на production не запускался. Длительное отсутствие повторения этим коротким наблюдением не доказывается.

## 8. Рекомендации

Держать Gunicorn за nginx; при следующем согласованном release перевести publish8000 на127.0.0.1 и согласовать firewall ownership. Добавить внешний healthcheck и метрики request queue/thread starvation/CLOSE_WAIT. Это рекомендации, не дополнительные выполненные изменения.

## 9. Итог и приоритет

Подтверждённый production инцидент доступности устранён в наблюдаемом окне. P1: исчерпание HTTP worker threads при прямом доступе к upstream. Источник/намеренность внешних соединений не доказаны. Версия приложения и данные сохранены; новая защита включена, публичный сайт отвечает200.
