# Specialist private-media operational transition

Stage24 prepares source/config only. Production has not been contacted, files moved, configuration activated or database migrated. This transition is a separate future release operation requiring its own explicit authorization and approved recovery plan.

1. Before activation, verify the exact release artifact and document reviewer assignments. Create a private filesystem root outside public MEDIA_ROOT with service-account-only traversal/read/write (directories0700, files0600), without a public nginx alias or storage URL. Never grant access merely through staff/Place/Organization management.
2. Audit existing SpecialistDocument records and disk files using restricted access. Keep only aggregate inventory/counts in repository reports; names, identity evidence, paths containing personal information and hashes that could identify evidence stay in restricted operational records. Identify missing files, symlinks, duplicate paths, unexpected formats and owner ambiguity; these require manual review. Legacy owner/is_verified/is_published values do not prove person claim or publication consent.
3. Plan and authorize the temporary access cutover. The checked-in nginx template denies /media/protected_docs/, /media/specialist-documents/ and /media/private-media/. Django DEBUG and SERVE_MEDIA_FILES apply the same guard. New files already use specialist-documents/<random>.bin under the separate private root. Existing public names are failclosed in the download endpoint until individually transitioned; no migration copies or deletes production bytes.
4. With writers paused through a separately approved operational procedure, copy approved inventory entries to freshly generated private names, reject symlinks/path traversal and verify byte equality plus restricted permissions. Preserve restricted mapping and originals for the authorized recovery window. Update each document path only after verified copy. Keep public consent unset; identity evidence can never become a public certificate. Uncertain records remain quarantined/inaccessible for manual review.
5. Verify with synthetic/authorized operational fixtures: anonymous and ordinary staff/volunteer/business managers cannot fetch identity evidence or direct URLs; the current verified person and dedicated active nonvolunteer document reviewer can fetch private attachment; only specialist-opted-in, KidsMap-approved certificate/diploma on an active published profile is public. Revocation, inactive account and claim replacement must immediately fail closed. Review permission and claim-review permission are separate.
6. Review the affected account-deletion cases against the already approved policy. The source hook revokes public consent and active employment authority, unlinks personal identities and anonymizes claim notes while preserving profile/review/location/employment history. It does not invent a new document-byte retention period or automatically delete historical evidence. Any byte retention/deletion policy clarification needs the privacy owner before production execution.
7. Roll back application/config only under the authorized release plan. Do not restore a public media bypass or silently reinstate publication consent. Preserve private copied files and restricted transition mappings; recovery must validate document paths and deny rules before enabling readers/writers.

Local validation uses synthetic bytes and disposable roots only: QA04 negative/integration tests plus qa24/nginx_probe.py against the actual source location rules with loopback HTTP/TLS removed. TLS certificate deployment, real storage permissions/legacy inventory, load, production release and transition execution are NOT RUN in stage24.
