# Языковые URL мест: локальная проверка и будущий выпуск

Дата: 2026-09-14. Реализация разрешена пользователем локально. Этот документ не разрешает запуск команд на сервере. Production не проверен и не изменён.

## Контракт

- AZ `/place/<id>-<slug_az>/`, RU `/ru/place/<id>-<slug_ru>/`, EN `/en/place/<id>-<slug_en>/`.
- Непустой языковой slug фиксируется при сохранении названия и больше не меняется обычным save/import. Частичное сохранение рейтинга/статуса не генерирует URL.
- Неизвестный перевод использует legacy `slug`; добавленный перевод получает адрес после сохранения. Бренды не переводятся искусственно.
- В существующих карточках AZ сохраняет legacy-адрес. Слишком длинный legacy slug остаётся fallback и требует ручного разбора при backfill; он не обрезается.
- Старый slug с тем же PK перенаправляет на текущий адрес языка. Закрытые места не раскрываются через redirect.
- `slug` остаётся уникальным идентификатором pricing API. Языковые поля не входят в editable payload volunteer.
- Настройка `LOCALIZED_PLACE_URLS_ENABLED`: по умолчанию включена только при `DEBUG=True` и `TESTING=False`. В production (`DEBUG=False`) и обычных тестах по умолчанию выключена. Браузерный стенд включает явно. Генерация полей при редактировании работает и до включения публичных URL.

## Изменённый процесс редактора

Открыть существующую инструкцию JSON → скопировать в ИИ вместе с материалами → импортировать JSON → проверить переводы/данные и блок адресов → сохранить. В инструкции добавлен раздел о названиях на трёх языках, брендах и автоматических URL. Схема JSON сохранена. Переданные `slug*`/URL-поля не применяются. `website` — официальный сайт организации.

При частичном JSON отсутствие тарифных полей сохраняет текущие тарифы. Явный `pricing_plans: []` очищает их; старые числовые цены продолжают преобразовываться серверным валидатором. Это исправляет обнаруженное браузерной проверкой превращение отсутствующих цен в пустой список. Кнопки URL используют настроенный `PUBLIC_BASE_URL`, а не случайный адрес админки.

На новом месте блок показывает предварительные окончания; ID появится после сохранения. На существующем месте показаны текущие адреса. Новые переводы получают адрес после сохранения, а изменение уже заполненного названия не переименовывает URL. Открыть публичный URL можно только для публично видимого места; скопировать можно и адрес черновика, не делая его публичным.

## Backfill

Команда `backfill_localized_place_slugs` по умолчанию только читает. Вывод — агрегатный JSON без записей мест/контактов. Примеры ниже выполняются исключительно в явно выбранном окружении с проверенными настройками:

```bash
python -m django backfill_localized_place_slugs --dry-run
python -m django backfill_localized_place_slugs --apply --batch-size 200
python -m django backfill_localized_place_slugs --apply --after-pk 123 --batch-size 200
```

`would_change` — кандидаты; `changed` — записанные карточки; `manual_review` — слишком длинный legacy либо конфликт с параллельным изменением; `unchanged` — записи без требуемых изменений, включая fallback. `last_pk` — последняя обработанная запись. После продолжения выполнить полный dry-run с нуля, чтобы вновь увидеть ранее пропущенные конфликты. Ошибка прерывает текущую порцию; предыдущие порции уже сохранены. Повторный полный запуск безопасен.

Применение пишет только пустые языковые поля через сравнение исходного снимка с текущей строкой. Не изменяет `updated_at`, статус, legacy slug, тарифы и расписание, не вызывает model save/signals и IndexNow. Максимальная порция 2000, PostgreSQL lock timeout 2 секунды и statement timeout 20 секунд на транзакцию. Длинный legacy AZ не обрезается. В процессе нет ИИ или перевода текстов.

## Порядок будущего серверного выпуска

1. Получить доступ и отдельное разрешение на server scope. Сверить deployed revision, миграции, окружение и текущий public origin; не выводить env/DSN/секреты в отчёты.
2. Согласовать конкретный diff с сохранением параллельных изменений проекта. На чистом staging повторить изолированные тесты и browser matrix.
3. Подтвердить доступность проверенного восстановления по release-контракту проекта. Никакие backup/deploy-команды не запускаются только потому, что они упомянуты здесь.
4. Установить schema migration `0113_place_localized_slugs` и совместимый код, оставив `LOCALIZED_PLACE_URLS_ENABLED=False` до подготовки данных.
5. Выполнить dry-run; разобрать `manual_review`. Применить backfill, повторить dry-run и проверить старые AZ-адреса и новый набор RU/EN.
6. Включить `LOCALIZED_PLACE_URLS_ENABLED=True`; проверить 200/301, canonical/hreflang/JSON-LD и sitemap на конкретных публичных местах. Сохранить направление старый → новый без циклов.
7. Проверить middleware/nginx для HTTPS, www, `/az/` и query-параметров. Локальные тесты дают один переход для старого slug на правильном origin; совмещённый `/az/` + неверный slug + лишний query даёт два. Production число переходов ещё неизвестно.
8. Ограниченно уведомить IndexNow и проверить sitemap в Search Console. Не отправлять уведомление на каждую запись из backfill. Проверить новое индексирование через 1–3 дня, 1–2 недели и месяц; это наблюдение, а не обещание роста выдачи.

## Восстановление без циклов

До публичной активации можно оставить флаг false и остановить backfill; поля не удалять и не откатывать всю БД поверх новых редакторских данных.

После выдачи постоянных редиректов нельзя просто вернуть флаг false или старый код: клиенты могут уже кэшировать старый → новый. Сохранить `LOCALIZED_PLACE_URLS_ENABLED=True`, языковые поля и совместимый resolver. Исправлять проблемный компонент на совместимой версии, сохраняя направление редиректов. Новые адреса и прежние redirect остаются даже при отключении проблемной UI-функции.

Отдельный recovery build для неизвестной будущей аварии не подготовлен. Перед production активацией проверить конкретный recovery diff на staging с уже кэшированным 301. Возврат на приложение до `0113` не является проверенным способом восстановления.

## Локальное окружение этой проверки

Создан отдельный tmpfs PostgreSQL 17 контейнер `kidsmap-url-test-db`, привязанный только к loopback порту 55439. Существующие контейнеры/базы не изменялись. Тестовые БД отделены от базы браузерных fixtures и получают отдельное имя; для root-runner имя включает PID, чтобы исключить пересечение запусков.

Media backend-тестов тоже получает отдельный каталог по PID. Фото браузерной fixture хранится отдельно: существующие map-тесты проверяют отсутствие физического файла и иначе получают другую сериализацию. Нельзя разделять media с браузерным стендом даже при разных БД.

Санитизированные настройки и runner находятся в `/tmp/kidsmap-url-tests/`; окружение запускается через `env -i`, `DJANGO_TESTING=1`, LocMem cache/email и временный media. Внешние аналитические/геокодирующие ключи отсутствуют. Браузерный стенд: `http://127.0.0.1:8769`, синтетические карточки и тестовые роли. Его данные не являются копией production.

В этом сеансе использовать `/tmp/kidsmap-url-tests/run-tests test <labels> --noinput`. Это wrapper для `.venv/bin/python -m django` из `/tmp`, с `/home/ramin/kidsmap/src` в PYTHONPATH. Такой запуск исключает затенение `src/config` корневым compatibility-пакетом `config`, обнаруженное при попытке `manage.py` из корня. Локальная среда `/tmp` временная; после её удаления повторно подготовить изолированные настройки/БД, не наследовать обычные production env.

Результаты и ограничения: `localized-place-urls-validation.md`, браузерные доказательства: `localized-place-urls-browser.md` в этой папке.
