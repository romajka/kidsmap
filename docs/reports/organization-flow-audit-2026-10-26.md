## 2. Сильные стороны

- В кабинете требуется только название AZ. Организация создаётся без филиала, адреса, координат и цен. Это правильное разделение Organization и Place.
- Переводы RU/EN, контакты и описание при создании уже спрятаны в раскрывающиеся блоки. Добавлять обязательный многошаговый мастер не нужно.
- В preview подключения указано, какие места подключатся сразу и какие потребуют согласия другого владельца. Нужна явная отметка согласия.
- На проверенном сценарии чужой филиал не подключился до подтверждения вторым владельцем. После подтверждения появился у сети.
- Обычный путь «изменения → модерация → одобрение» дал публичную карточку с двумя филиалами и HTTP 200 для гостя.
- В 75 замерах пяти поверхностей × RU/AZ/EN × 390/768/1024/1280/1440 px документ не имел горизонтального переполнения. Это геометрический результат, не полная WCAG-приёмка.

## 3. Реальные проблемы

Все findings ниже: **LOCAL WORKTREE + isolated fixture DB**, воспроизводимость подтверждена браузером и/или отдельным backend probe. Production-наличие не утверждается. Confidence: high, кроме явно отмеченной интерпретации UX.

### ORG-A01 — Счётчики завышены при нескольких филиалах — P2

**Факт:** в окончательной fixture DB три организации; админка показывает четыре. Две записи имеют `status=published`, счётчик показывает три. Ранее при двух организациях и двух филиалах одной сети отображалось «всего 3», хотя таблица содержала две строки.

**Причина:** `src/catalog/domain_admin/business.py:424`, `_dashboard_counts`: агрегаты `Count("id")` не distinct, а в том же запросе есть JOIN на places. Только `with_places` считает distinct.

**Влияние:** администратор не может доверять сводке. Owner: Django / database; следующий шаг — единый набор query predicates для counts и filters, тест на 0/1/2 филиала и архивные связи. Evidence: `backend-facts.json`, `screenshots/admin-counts-and-queue.png`.

### ORG-A02 — Очередь «На модерации» не видит ожидающую версию — P2

**Факт:** владелец отправил изменения, кабинет показал «Изменения на модерации», revision стала pending. В админке «На модерации 0» и пустая отфильтрованная таблица. При прямом открытии организации доступны diff и «Одобрить заявку».

**Причина:** counts/quick filters в `domain_admin/business.py:_dashboard_counts/_quick_filters` смотрят на `Organization.status`; `services/publication.py:326`, `propose`, хранит ожидание изменений в revision. Это разные сущности состояния.

**Влияние:** заявка может остаться незамеченной. Owner: Django; следующий шаг — показывать публикацию и ожидающие изменения отдельно, фильтровать revisions через общий predicate. Evidence: `functional-facts.json` → `adminQueue`, `emptyPendingQueue`.

### ORG-A03 — Массовое «Опубликовать» даёт ложный успех и public 404 — P2

**Факт:** созданную через админку организацию выбрали в списке и применили массовую публикацию. Строка стала «Опубликовано». При этом `approved_at` пуст, revision всё ещё draft, гостевой запрос карточки вернул 404. Другая организация после обычного одобрения вернула 200.

**Причина:** `domain_admin/business.py:562`, `mark_published`, напрямую меняет `status`. Public contract в `controllers/organization_directory.py:40` требует также одобрение и отсутствие архива. Обычные переходы идут через publication service.

**Влияние:** интерфейс обещает недостигнутый результат. Не доказаны ни production-инцидент, ни эксплуатация прав доступа. Owner: Django; dependency: security review ограниченных staff permissions. Следующий шаг — общие проверяемые переходы для обычных и массовых действий, с пообъектным результатом и проверками версий/прав. Evidence: `backend-facts.json`.

### ORG-A04 — Обязательность AZ скрыта, при ошибке админка теряет ввод — P2

**Факт:** AZ визуально не обязательное и `OrganizationForm.fields['name_az'].required=False`. При заполнении только RU сервер отвечает `Azerbaijani name required.`, перенаправляет назад и стирает введённое RU-значение. В кабинете AZ отмечено обязательным и ошибка выводится в форме.

**Причина:** `domain_admin/business.py:59`, OrganizationForm; `:283`, `BusinessEditor.changeform_view`, ловит ValidationError и возвращает redirect. Реальное требование находится в `services/organization_ownership.py:94`, `_create`.

**Влияние:** потеря незаписанного пользовательского ввода и неясное исправление. Owner: Django / frontend-admin. Следующий шаг — required + field error на bound form без redirect, согласованная локализация. Evidence: `functional-facts.json` → `adminMissingAz`; `screenshots/admin-error-lost-input.png`.

### ORG-A05 — Создание и редактирование по-разному проверяют контакты — P2

**Факт:** создание владельцем с `phone=not-a-phone` прошло, строка сохранена в draft. Редактирование с новым неверным телефоном отклоняется, но показывает общий текст «Не удалось отправить изменения…» без указания поля.

**Причина:** `controllers/organization_workspace.py:163` — обычные CharFields; `_create` не использует contact normalization. `services/publication.py:169`, `_validate_patch`, использует `normalize_contact_patch`. `organization_workspace.py:211`, `_organization_save_errors`, сводит немаппированные ошибки к общей.

**Влияние:** мусорные контакты в черновике и непонятная ошибка исправления. Прохождение такого контакта через публикацию не проверено и не утверждается. Owner: Django; dependency: общий контактный контракт. Следующий шаг — единый валидатор новых/изменённых контактов, привязка ошибок к полю; не блокировать без причины неизменённые исторические данные.

### ORG-A06 — После создания видны все инструменты сразу — P2 UX

**Факт:** на первом рабочем экране нового владельца одновременно четыре формы: филиал, программа, команда, профиль — 13 видимых полей/селектов. При ширине 1280 px документ около 4137 px высотой. Навигация разделов — якоря, а не переключение содержимого. «Пригласить сотрудников» выглядит третьим обязательным шагом запуска; публикация отдельным шагом не показана.

На 390 px поле названия на экране создания оказалось примерно на y=1105 px документа: основное действие отодвигается большим пояснением. Измерение зависит от состояния раскрывающихся блоков/черновика; факт ухода названия ниже первого экрана подтверждён скриншотом.

**Source:** `templates/pages/organization_create.html:31`, guide; `organization_workspace.html:185`, onboarding; `controllers/organization_workspace.py:289`, `_detail_context`. `has_details` означает наличие хотя бы одного описания/контакта, а не полноценную готовность к публикации.

**Влияние:** трудно понять следующее нужное действие. Confidence high для замеров, medium для оценки удобства без исследования. Owner: frontend-reviewer / frontend-admin. Следующий шаг — контекстные действия и реальные вкладки, команда/программы в дополнительные инструменты. Evidence: `functional-facts.json`, `responsive.json`, screenshots owner-*.

### ORG-A07 — Самостоятельное место помечается как устаревшая связь — P2

**Факт:** до подключения собственного самостоятельного места на странице организаций показано «Связь неактуальна: доступ сети не действует».

**Причина:** `templates/pages/organization_workspace.html:102`, проверка `not place.affiliation_is_current` применяется к самостоятельным местам, для которых действующая связь с сетью не ожидается.

**Влияние:** пользователь видит несуществующую проблему доступа. Owner: frontend-reviewer; следующий шаг — различать standalone, pending, current и stale, брать значения из backend context. Evidence: `functional-facts.json` → `ownerStandaloneWarning`.

### ORG-A08 — Подтверждению чужого филиала не хватает контекста — P2 UX

**Факт:** второй владелец увидел уведомление «Подтвердите связь» и кнопку «Подтвердить связь» без названий сети и места. Кнопка сразу подтвердила связь и открыла список мест.

**Source:** `templates/pages/account_notifications.html:18`, `:26`.

**Влияние:** согласие технически получено, но пользователю недостаточно информации для решения. Отсутствие проверок прав не утверждается: проверенный поток верно ждал второго владельца. Owner: frontend-reviewer / Django; следующий шаг — названия обеих сторон и preview последствий с актуальными версиями, не обходить existing request/confirm services.

### ORG-A09 — Дублирование, пустая техническая вкладка и неполная локализация — P3

Пять KPI повторяют пять фильтров по статусам, таблица содержит слабо полезные для первого просмотра столбцы. В форме админа вкладка «Основная информация / General» фактически содержит hidden versions и не даёт полезного шага. В EN остаются русские тексты «Управляйте организациями…», «Добавить организацию», «С филиалами». Геометрический PASS не означает завершённый перевод.

Owner: frontend-admin / localization. Следующий шаг — один ряд фильтров со счётчиками, минимальные колонки, убрать вкладку без видимого содержимого, перевести весь затронутый маршрут.

## 4. Tech debt

- Обычный review и bulk status update реализуют разные значения «опубликовано».
- Publication status смешан с moderation status candidate-версии; UI не имеет одного представления состояния.
- Сервис создания и сервис изменения имеют разные validation paths для одного контакта.
- Общий BusinessEditor используется также другими бизнес-сущностями: правки обработки ошибок/hidden sections требуют репрезентативной проверки этих редакторов, не переписывания всего модуля.
- Прогресс запуска — локальные bool-флаги, не контракт публикации. Не заменять их новым независимым JS-процентом.

## 5. Risks и продуктовые решения

- Создание через админку назначает создавшего staff владельцем. Это подтверждённое поведение, но выбор ожидаемого продукта требует решения: «создаю для себя» или «создаю для другого владельца». Не менять собственника прямым FK-редактированием; использовать проверенные ownership/handover services.
- В публичной карточке при заполненном phone и пустом whatsapp появился `wa.me` на тот же номер. Подтверждено по DOM. Телефон не доказывает доступность WhatsApp; предложено явное согласие «WhatsApp на этом номере». Массовая правка старых контактов не входит в scope.
- Скрытие команды/программ — только presentation. ACL, CSRF, version conflict, confirmed affiliation и отдельная публикация филиалов должны сохраниться.
- Добавление филиала не должно автоматически публиковать draft Place. Публикация сети не означает публичность всех мест.

## 8. Рекомендации

**Лучший вариант: короткое создание + постепенное раскрытие возможностей.** Дополнительный обязательный мастер увеличит работу пользователя и не исправит нынешние ошибки.

| Данные/действие | Где показывать |
|---|---|
| Название AZ | Единственное обязательное поле создания |
| Переводы RU/EN | Необязательный свёрнутый блок профиля |
| Короткое описание и контакты | Необязательно при создании, доступны в профиле; без выдуманных публикационных требований |
| Адрес, карта, возраст, цены, расписание | В конкретном Place/филиале |
| Добавить / подключить первый филиал | Главный следующий CTA после создания; можно пропустить |
| Отправить сведения / одобрить / опубликовано | Ясный статус и следующий доступный шаг, отдельно от филиалов |
| Программы, сотрудники, специалисты | «Дополнительно», по запросу пользователя |

Путь: **название → профиль создан → добавить/подключить филиал или позже → отправить сведения на проверку → одобрено/опубликовано**. Отдельные состояния: публикация организации, ожидающие изменения, подтверждение связи места и публикация самого места.

Рабочий экран: настоящие разделы **«Филиалы / Профиль / Дополнительно»**. В новом профиле одна основная кнопка «Добавить филиал» с выбором «Создать новое место» / «Подключить существующее». В профиле без ожидания публикации — контекстная кнопка проверки сведений; при pending — показать ожидание и доступные безопасные действия. Команда не должна влиять на готовность запуска.

Админский список: один ряд фильтров с достоверными счётчиками; основные колонки «Название / Публикация и изменения / Владелец / Филиалы / Обновлено». Телефон/программы — дополнительные колонки. В пустой строке филиалов полезнее «Добавить», чем тире.

Порядок: сначала достоверность публикации, очереди и счётчиков; затем validation/error recovery; затем UX, контекст подтверждения и локализация. План: `docs/plans/organization-flow-2026-10-26.md`.
