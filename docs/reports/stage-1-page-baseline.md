## Как повторить

Использовались Python 3.12.3, Django 6.0.9, локальный PostgreSQL 17.11 по TCP и Gunicorn 23.0.0 с одним воркером `gthread` и четырьмя потоками. Для замеров — изолированные БД и media, `DJANGO_TESTING=1`, `DEBUG=False`, LocMemCache, отключённые внешние интеграции. SQL-тест очищает Django-кэш перед каждым URL. HTTP-замер начинает каждый размер фикстуры со свежим процессом Gunicorn, затем отправляет запросы последовательно без сброса кэша между повторами. TTFB отсчитывается до первого байта HTTP-ответа. Временные значения зависят от машины и нагрузки.

В одноразовой локальной базе с применёнными миграциями выполнить бюджет отдельно:

```sh
python manage.py test catalog.testcases.test_query_budget -v 2
```

Для HTTP-замера заполнить новую пустую базу того же **изолированного тестового профиля**. Каждые пять опубликованных мест добавляют одно публичное событие и одного специалиста. Получаются 20/4/4 и 60/12/12 записей соответственно. Карточка и тематическая подборка в обоих замерах одни и те же.

```sh
python manage.py shell -c "from django.conf import settings; assert settings.TESTING; from catalog.testcases.test_query_budget import add_places, create_page_fixture, fixture_pages; place = add_places(create_page_fixture(), 1, 20); print(fixture_pages(place)['place'][0])"
```

Запустить локальный Gunicorn в этом профиле и передать выведенный путь карточки в список. Здесь использован путь из замера:

```sh
python scripts/measure_pages.py --base http://127.0.0.1:33731 \
  / /ru/ /ru/catalog/ /ru/events/ /ru/specialists/ \
  /ru/place/stage1-judo-20/ /ru/catalog/dzudo-dlya-detey-v-baku/
```

Для второго замера добавить ещё 40 мест, перезапустить локальный Gunicorn и повторить ту же команду:

```sh
python manage.py shell -c "from django.conf import settings; assert settings.TESTING; from catalog.models import Subcategory; from catalog.testcases.test_query_budget import add_places; add_places(Subcategory.objects.get(code='judo'), 21, 60)"
```

## Проверки этапа

- Полный изолированный прогон Django на PostgreSQL завершился успешно. Из 4287 тестов 4281 прошёл, три пропущены, три дали ожидаемый результат `expectedFailure`, описанный выше. `makemigrations --check --dry-run` не обнаружил изменений моделей.
- В отдельном прогоне Python-скриптов прошли 70 тестов из 71. Один тест предназначен для Windows. На SQLite повторно прошли проверки middleware, Sentry и SQL-бюджетов с теми же тремя `expectedFailure`.
- Четыре одновременных запроса с 1, 2, 3 и 4 SQL-вызовами получили собственные счётчики. В проверке через локальный Gunicorn запрос к API создал одну строку, обращения к static, media, favicon и `/healthz` — ноль. У всех ответов были две длительности в `Server-Timing`.
- Docker Compose передал обе переменные в окружение `web`. Настройки работающего SDK и включение `DjangoIntegration` проверены локально с отключённым сетевым транспортом.
