# Place JSON import and export

The current instruction is generated by `static/admin/js/kidsmap_place_json_import.js` from the form's taxonomy and pricing contract. The administrator and volunteer share it. The owner form uses the same pricing/schedule validators but does not expose this JSON dialog. Historical QA reports and the old field matrix are not an import schema.

## Identity and partial updates

Import one object, optionally inside a JSON code fence and followed by notes. A complete export carries `schema_version`, `place_id` and `base_content_version`; use a fresh export of the same place. Another place's identity, a stale content version and an unsupported schema version must be rejected.

If a saved draft/pending/rejected candidate exists, export includes that candidate's text, direct tariffs, structured schedule and nested pricing. `export_scope` distinguishes `candidate` from `stored`; `candidate_version` rejects an outdated candidate export. Unsaved browser edits are not included. Volunteers can validate an identified update only for their own eligible cards; they obtain a fresh export from an administrator. This does not grant access to the normal administrator change page or another author's cards.

Omitted keys and `null` represent unknown or unchanged data. Explicit empty text clears that text; required fields still have to pass validation before publication. An explicit empty `pricing_plans` list requests removal of direct relational tariffs, with confirmation. Omitted pricing keeps existing prices. Imported values first populate the form; import success is not a database-save or publication receipt.

## Prices and legacy data

`pricing_plans` uses the model's product, billing, price-kind, unit, audience and day enums. The generated instruction supplies current choices and working examples. `quantity`/`quantity_unit`, recurring payment frequency, purchased-use validity and offer dates are separate concepts. Do not infer unlimited visits, billing frequency or expiry from one another. New prices use AZN; preserve existing currencies and exact periods from an export.

Exports also retain original scalar price fields and `pricing_plans_legacy` for recovery and manual review. These historical fields are not permission to infer a new product or automatically rewrite a card. Preserve unchanged historical JSON when editing another field. For ambiguous `{name, price, frequency}` entries or scalar ranges without a unit, confirm their business meaning before replacing them with canonical tariffs. Do not run a bulk migration as part of a normal edit.

Version 1 exports direct place tariffs. `?pricing_schema_version=2` additionally exports `nested_pricing` with activities and groups. Import nested pricing only for an existing place and retain its IDs and complete structure. A direct-only export is not an export of all group tariffs.

## Schedule, contacts and media

Structured `schedule_days` describes the full week (`mon` through `sun`) with closed/24-hour flags and non-overlapping time intervals. `schedule` is the historical text fallback. Preserve it when the exact structured week is unknown. Modes are supplied by the backend, including by-appointment, variable, event-based and always-open schedules. Do not turn unknown days into closed days.

Phone slots are `phone1` through `phone3`, with `phone_country`; WhatsApp uses `same`, `separate` or `none`, with an optional separate number. Unknown WhatsApp mode is `null`, not an invented claim. Named `public_links` allow at most five HTTP(S) links.

Photos are uploaded through the editor. JSON does not fetch remote photo URLs, replace binaries, or restore a gallery. `editor_review.media_to_upload` is a human task list. A successful JSON round trip does not establish a photo export/import round trip. Unknown fields must be disclosed to the user, never presented as saved data.

The pricing-check endpoint checks tariff/contact compatibility and identity; final form/schedule/publication validators remain authoritative. An imported example with missing place facts is a draft, not a publication-ready card.

## Field coverage and manual tasks

The administrator's new and existing-place forms include the advertised place-wide `lesson_format`, `lessons_per_week` and `lessons_per_month` controls under the optional place features. They are independent of the corresponding per-tariff frequency and quantity fields. The three `custom_price_badge_*` fields retain their saved values on reopening; leaving a saved text badge untouched must not clear it.

Tariff examples include all five price kinds, recurring and installment billing, mandatory paid services and registration fees. Installment `price` is the total confirmed price and `billing_cycles` is the payment count. The importer rejects unknown field names inside direct and group tariffs before changing the form; supported legacy aliases and presentation keys from exports remain accepted.

`editor_review` is displayed as an import checklist and is not stored as place content. Keep the original JSON and research report separately. Media binaries, unresolved facts, staff verification, ownership and publication approval require their own workflow. The permanent-place editor does not change card type in response to `is_temporary`; select the correct creation workflow first.
