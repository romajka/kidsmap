## Продуктовый контракт

### 1. Как выглядит результат

Условное место с ID 123:

| Язык | Название | Адрес |
|---|---|---|
| AZ | Oyuncaq Muzeyi | `/place/123-oyuncaq-muzeyi/` |
| RU | Музей игрушек | `/ru/place/123-muzei-igrushek/` |
| EN | Toy Museum | `/en/place/123-toy-museum/` |

Точное русское окончание определяется действующей таблицей транслитерации; пример обозначает форму адреса, а не новую таблицу правил. Сохраняем `/place/`, числовой ID и AZ без префикса. Перевод служебного сегмента, удаление ID и смена домена не входят в задачу.

Google рекомендует слова на языке аудитории, включая транслитерацию. Это улучшение понятности адреса, а не обещание роста позиций. [Google: структура URL](https://developers.google.com/search/docs/crawling-indexing/url-structure).

### 2. Добавление и редактирование

1. Редактор открывает существующую «Инструкцию для создания JSON», копирует её и передаёт ИИ материалы о месте.
2. ИИ возвращает существующий JSON, уделяя явное внимание `name_az`, `name_ru`, `name_en`. Собственные переводы отмечает в `editor_review.generated_translations`.
3. Импорт заполняет форму. Сайт показывает три предварительных адреса; до сохранения у нового места ID ещё нет, поэтому текст: «ID будет добавлен после сохранения».
4. Backend при сохранении впервые заполняет отсутствующие языковые окончания. После сохранения админка показывает точные URL с действиями «Скопировать» и, для публичного места, «Открыть».
5. Обычное изменение названия и повторный импорт не меняют уже сохранённые URL — даже у черновика. Это более простое и предсказуемое правило, чем зависимость от статуса публикации.
6. У существующего места ранее пустой языковой slug может появиться при добавлении перевода. Прежний fallback-адрес становится 301 на новый адрес в том же языке.
7. Ручной редактор опубликованных адресов и массовое переименование не входят в первую реализацию. Коррекция ошибочно зафиксированного slug — отдельный ограниченный scope с просмотром старого и нового адреса.

ИИ не возвращает `slug`, `slug_az`, `slug_ru`, `slug_en` или полный URL карточки. Поле `website` продолжает означать официальный сайт организации. Это исключает ручную работу с транслитерацией и случайное изменение ссылок через JSON.

### 3. Имена и достоверность

- Официальный бренд сохраняется: `Kids Planet` может быть одинаковым на трёх языках. Не переводить бренд буквально и не придумывать официальную локализованную форму.
- Описательные названия переводить естественно, без дополнительных SEO-слов, района или услуг, отсутствующих в исходном названии.
- Переводить можно только известное название; нельзя выдумывать название или факты при отсутствии источника.
- Если качественный перевод невозможен, оставить поле пустым и объяснить в `editor_review.needs_verification`. Существующие требования к публикации не ужесточать ради URL.
- Сохраняются все нынешние правила о ценах, расписании, контактах, координатах, фото, источниках, конфликтах и формате JSON.

### 4. Данные и адреса

- Добавить `slug_az`, `slug_ru`, `slug_en`: строка до 60 символов, `blank=True`, `default=""`, без отдельной уникальности. Уникальность полного URL обеспечивает существующий PK. Старый уникальный `slug` не переименовывать и не удалять: от него зависит pricing API.
- Формат новых значений: строчные ASCII-буквы, цифры и одиночные дефисы. Использовать `build_ascii_slug` и действующую `ASCII_TRANSLITERATION_MAP`, не вводить вторую транслитерацию в JS.
- Создание: для каждого непустого `name_<lang>` вычислить slug только при пустом `slug_<lang>`. Если после нормализации не осталось букв/цифр, оставить языковое поле пустым и использовать legacy fallback.
- Чтение: `slug_<lang>`, если заполнен, иначе текущий `slug`. Никакой генерации и записи при GET, рендере sitemap или переключении языка.
- Сохранение с `update_fields` должно включать реально добавленные языковые поля. При ограниченном сохранении не генерировать slug из несохранённого изменения названия; брать только сохранённое имя либо имя, входящее в `update_fields`.
- Одновременные сохранения: заполнение пустого поля атомарно, уже заполненное значение не перезаписывается устаревшим экземпляром. Отдельно проверить взаимодействие с `post_save`/IndexNow.
- Старые записи: сохранить существующий AZ-адрес, записав `slug_az = slug`. Для RU/EN заполнить пустые поля из существующих переводов. Не вызывать ИИ и не переводить каталог во время миграции.
- Это правило сохранения AZ действует и при обычном `save()` существующей записи до backfill: если у объекта уже есть PK и legacy slug, пустой `slug_az` заполняется legacy-значением. Для нового объекта AZ генерируется из `name_az`. Так редактирование во время подготовительного выпуска не меняет старые AZ-адреса.
- Если перевод отсутствует, сохраняется общий slug. Новое правило индексации непереведённых страниц не входит в этот scope: перевод URL не делает содержимое страницы переведённым.
- При внешнем импорте/`bulk_create`, обходящем `save`, разрешён fallback. Импортёр должен явно вызвать сервис заполнения, если требуется сразу получить локализованные URL.

### 5. Старые ссылки и SEO

- Место по-прежнему ищется по PK через действующий фильтр публичной видимости. Только после этого сравнивается slug текущего языка.
- Канонический URL даёт 200; старый общий slug, slug другого языка и произвольное неверное окончание с существующим публичным PK дают 301 на канонический URL текущего языка.
- `/place/<pk>/` сохраняется как legacy-маршрут и направляет сразу на конечный адрес языка запроса.
- Черновое, удалённое, скрытое и несуществующее место не раскрывается через редирект; применяется нынешняя публичная политика ответа.
- Таблица истории URL не нужна: PK уже присутствует во всех текущих адресах мест. Любая старая текстовая часть разрешается через этот PK. Это решение не распространяется на сущности с маршрутами только по slug.
- Canonical каждой языковой страницы указывает на неё саму. `hreflang` содержит взаимные прямые конечные URL, `x-default` — AZ. Переключатель языка использует эти же адреса. [Google: языковые версии](https://developers.google.com/search/docs/specialty/international/localized-versions).
- Sitemap, внутренние ссылки, Open Graph и URL в JSON-LD используют тот же построитель. Сохранить существующую фильтрацию публичной видимости и параметры каталогов.
- В пределах уже правильных origin/языкового префикса переход старого slug должен занимать один 301. Комбинации HTTP/HTTPS, www, `/az/` и лишних query-параметров проверить отдельно с middleware; не обещать один hop на уровне неизвестной production-конфигурации.
- Старые редиректы сохранять постоянно; минимальный ориентир Google при смене URL — не менее года. Не закрывать старые адреса в robots.txt. [Google: смена URL](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes).

Минимальный пример проверки стабильности, входящий в новый test module:

```python
from django.test import TestCase, override_settings
from catalog.models import Place
from catalog.services.place_urls import place_path_for_language

@override_settings(LOCALIZED_PLACE_URLS_ENABLED=True)
class LocalizedPlaceUrlTests(TestCase):
    def test_saved_english_url_survives_rename(self):
        place = Place.objects.create(name="Toy Museum", name_en="Toy Museum",
                                     category="EDU", status="draft", is_active=False)
        before = place_path_for_language(place, "en")
        self.assertEqual(before, f"/en/place/{place.pk}-toy-museum/")
        place.name_en = "New Museum Name"
        place.save(update_fields={"name_en"})
        place.refresh_from_db()
        self.assertEqual(place_path_for_language(place, "en"), before)
```
