# Изолированные проверки KidsMap

Установить зависимости тестового окружения: `python -m pip install -r requirements-test.txt`.
Для Linux нужны gettext, компилятор C, pkg-config и dev-библиотеки MariaDB/MySQL для существующего mysqlclient. PostgreSQL для тестов запускается отдельно, без сетевого интерфейса; пример подготовки есть в `.github/workflows/deploy.yml`.

## Полный запуск

На каждый запуск нужны **новый QA04 профиль и новый собственный PostgreSQL**. Скрипт проверяет фактические БД/роль/Unix socket, очищает унаследованные credentials и использует отдельные cache, media, email и переводы. Существующий профиль автоматически не переиспользуется: transaction/migration тесты могут удалить данные, созданные data migrations.

```bash
python scripts/run_isolated_quality.py \
  --profile-root /tmp/kidsmap-task33-qa04-MY-RUN \
  --socket-dir "$PWD/.tmp/kidsmap-task33-qa04-socket-MY-RUN/socket" \
  --execution split --workers 4
```

Каталоги и PostgreSQL в примере должны быть подготовлены заранее. Число workers допускается от 1 до 16; сначала использовать 4, а не число всех доступных CPU.

`split` запускает обычные тесты в отдельных процессах, затем чувствительные проверки последовательно. В последовательную часть попадают TransactionTestCase, известные migration/conversion/crash модули, обнаруженные прямые QA guards и случаи с неизвестным типом или недоступным исходником. Для дополнительной общей файловой/процессной зависимости установить у класса `quality_serial = True` или Django tag `quality_serial`. Такой тест остаётся в полном gate.

Рабочие процессы получают собственные каталоги `QA_ROOT/workers/PID/`. Проверки миграций и конвертации продолжают работать в `test_qa_stage04`; их защитные условия сохраняются.

Наборы получаются из одной canonical discovery. Gate проверяет состав и уникальность ID, сверяет фактически выполненные тесты с планом и возвращает ошибку при потере/повторе/падении. Ошибка параллельной части останавливает запуск до последовательной. Пустой выбор тестов не считается успешным прогоном.

Для диагностики выполнить тот же вызов с `--execution serial` на новом окружении. Простое `manage.py test --parallel` для набора с чувствительными тестами отклоняется: использовать полный split gate.

## Пока идёт разработка

Передать после опций явные canonical labels затронутых модулей, например `catalog.testcases.test_module13_discovery`. Это **целевая проверка**, а не полная приёмка.

После небольшого изменения достаточно затронутого модуля и общих сценариев, на которые оно влияет. Полный набор модуля выполнить после завершения его правок; полный gate проекта — перед окончательной приёмкой. Повторять полный прогон без новых изменений, ошибок или неразрешённых рисков не нужно.

## Отчёт времени

По умолчанию `PROFILE/timing.json` содержит:

- полный план ID, записи выполненных тестов и явные missing/extra IDs;
- результат, число ошибок/пропусков, время и PID каждого теста;
- время collection, подготовки/закрытия БД, checks и выполнения каждой части;
- время полного CLI gate, версии Python/Django и контроль неизменности исходников.

Время теста включает его instance setUp/body/tearDown. Общие setUpClass/setUpTestData и class cleanups входят во время выполнения части; они не приписываются отдельному методу. Для сравнения отдельных fixtures это ограничение нужно учитывать.

`PROFILE/source-entry.json` связывает результат с исходниками. При изменении исходников во время gate результат считается неуспешным. Для предписанного снимка можно передать `--source-manifest FILE` с объектом `{"sources": {"relative/path": "sha256"}}`; этот список проверяется до и после запуска.

`--timing-json PATH` меняет путь общего отчёта. Частичные отчёты `timing-parallel.json` / `timing-serial.json` остаются в профиле, в том числе при падении тестов. Отчёт не содержит содержимое БД, email, credentials или stdout тестов. GitHub CI сохраняет отчёты как артефакт; полный Django gate продолжает блокировать deploy при любой ошибке. JS, реально отрендеренная фотоформа и browser acceptance остаются отдельными обязательными шагами CI.
