## 1.2 · План

Проверю полные HTTP-запросы и оба singleton в models/site.py, middleware, feature switches и тестах бюджетов. В исходнике четыре public view уже ограничивают чтение SiteSettings временем рендера. Измерю другие страницы и чтение CatalogContentSettings. Проверю раздельность запросов, сброс при сохранении, proxy админки и поведение вне HTTP. Сгруппирую повторные SQL главной и по результатам снижу потолки. Основной риск — повторное использование изменяемого объекта настроек за пределами запроса.

На базе 0f5c95e6 новый HTTP-тест дал 2 SELECT вместо 1 для каждой таблицы на обоих последовательных запросах. После установки middleware тот же сценарий читает каждую таблицу ровно один раз. Запросы после изменения строки видят новые данные. Проверены сохранение proxy бренда, обновление контента каталога и чтение вне HTTP.

Диагностика SQL на PostgreSQL 17, 20 мест и 4 события, холодный кеш. В исходной главной 39 запросов, из них 1 к SiteSettings и 1 к CatalogContentSettings. Четыре отдельных SELECT категории идут из Event.get_category_display при отрисовке карточек. query_public_events теперь использует select_related для категории. Это убрало рост SQL на обеих главных и афише, поэтому три expectedFailure сняты в 1.2. Исходные утверждения остались прежними.
