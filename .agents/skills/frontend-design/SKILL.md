# Frontend Design

Используй этот skill, когда задача связана не только с функциональностью, но и с визуальным качеством интерфейса.

## Главная цель

Создавать интерфейс, который выглядит как работа профессионального продуктового дизайнера, а не как типичный автоматически сгенерированный UI.

Интерфейс должен быть:
- визуально цельным;
- понятным без объяснений;
- аккуратным;
- современным;
- функциональным;
- адаптивным;
- удобным для реального пользователя.

## Перед изменением интерфейса

Не начинай сразу менять CSS.

Сначала:

1. Изучи существующую страницу и связанные компоненты.
2. Определи назначение интерфейса и основное действие пользователя.
3. Определи визуальные проблемы:
   - слабая иерархия;
   - неправильные отступы;
   - плохое выравнивание;
   - перегрузка;
   - слишком много рамок;
   - плохая типографика;
   - непонятные кнопки;
   - несогласованные размеры;
   - проблемы responsive;
   - визуально слабые empty/error/disabled states.
4. Изучи существующие CSS variables, компоненты и design tokens.
5. Переиспользуй существующую систему, если она качественная.
6. Не создавай новый визуальный язык для каждого компонента.

## Визуальная иерархия

Пользователь должен мгновенно понимать:
1. что это;
2. какая информация главная;
3. что второстепенно;
4. куда нажать;
5. что произойдёт после действия.

Используй размер, насыщенность, пространство, группировку и контраст осмысленно.

Не выделяй всё одновременно.

## Layout и spacing

Следи за:
- вертикальным ритмом;
- одинаковыми внутренними отступами;
- логичными промежутками между группами;
- выравниванием элементов;
- общей сеткой страницы;
- плотностью интерфейса.

Связанные элементы должны визуально находиться ближе друг к другу, чем несвязанные.

Не исправляй плохую композицию случайными margin/padding для каждого отдельного элемента. Сначала найди системную причину.

## Типографика

Используй ограниченное количество размеров и начертаний.

Создавай ясную иерархию:
- заголовок;
- подзаголовок;
- основной текст;
- вторичная информация;
- labels;
- helper/error text.

Следи за:
- line-height;
- длиной строки;
- переносами;
- визуальной плотностью.

Не уменьшай текст только ради того, чтобы всё поместилось.

## Компоненты

Для каждого интерактивного компонента учитывай при необходимости:
- default;
- hover;
- focus;
- active;
- disabled;
- loading;
- error;
- success;
- empty state.

Интерактивные элементы должны визуально отличаться от обычного текста.

## Кнопки

Должна быть понятная иерархия действий:
- primary;
- secondary;
- tertiary/destructive при необходимости.

Не превращай каждое действие в яркую primary-кнопку.

Не используй несколько конкурирующих главных CTA в одном небольшом блоке без причины.

## Карточки

Не заключай каждую группу информации в отдельную карточку только потому, что это удобно технически.

Используй контейнеры и рамки только когда они помогают:
- группировке;
- иерархии;
- кликабельности;
- отделению самостоятельной сущности.

Избегай "карточка внутри карточки внутри карточки".

## Цвет

Цвет должен иметь назначение.

Используй его для:
- бренда;
- состояния;
- акцента;
- важного действия;
- смысловой категории.

Не добавляй случайные градиенты, glow, glassmorphism или декоративные эффекты без визуальной причины.

## Иконки

Используй единый набор иконок и единый визуальный стиль.

Не смешивай случайные SVG, emoji и разные icon libraries.

Иконка должна помогать распознаванию действия, а не быть украшением ради украшения.

## Motion

Анимация допустима, если она:
- показывает изменение состояния;
- помогает понять переход;
- делает взаимодействие естественнее.

Предпочитай короткие и ненавязчивые transitions.

Не добавляй анимацию только для демонстрации возможностей.

## Responsive

Интерфейс должен проектироваться как адаптивная система, а не как desktop, который потом пытаются уменьшить.

Минимально проверить:
- 375px;
- 768px;
- 1024px;
- 1440px.

Проверять:
- overflow;
- перенос текста;
- размеры touch targets;
- расположение кнопок;
- таблицы;
- формы;
- dropdown;
- модальные окна;
- длинные названия;
- изображения.

## Accessibility

Не ухудшай:
- keyboard navigation;
- focus indicators;
- semantic HTML;
- labels;
- contrast;
- aria-атрибуты;
- работу screen reader.

Не заменяй button/div и link/div без причины.

## Работа с существующим проектом

При редизайне существующего проекта:

- не меняй backend-логику без необходимости;
- не изменяй API-контракты ради визуальной правки;
- не удаляй существующие состояния;
- не ломай JavaScript handlers;
- не переименовывай selectors без проверки их использования;
- ищи все связанные файлы перед существенными изменениями.

Визуальный рефакторинг не должен становиться функциональным рефакторингом без необходимости.

## Обязательная визуальная проверка

Если доступен Chrome DevTools MCP или другой браузерный инструмент:

1. Открой реальную страницу.
2. Проверь результат непосредственно в браузере.
3. Исследуй DOM и computed styles при проблемах.
4. Проверь Console.
5. Проверь responsive.
6. Исправь обнаруженные визуальные дефекты.
7. Повтори проверку.

Не считать визуальную задачу завершённой только потому, что CSS выглядит правильным в исходном коде.

## Приоритет решений

При выборе между эффектностью и понятностью:

1. usability;
2. visual hierarchy;
3. consistency;
4. responsiveness;
5. accessibility;
6. эстетика;
7. декоративные эффекты.

## Финальная самопроверка

Перед завершением спроси себя:

- Понятно ли главное действие?
- Улучшилась ли иерархия?
- Стало ли меньше визуального шума?
- Все ли элементы выровнены?
- Системны ли отступы?
- Не появилось ли лишних рамок?
- Хорошо ли выглядит mobile?
- Выдерживает ли дизайн длинный текст?
- Проверен ли реальный результат в браузере?
- Не сломана ли существующая функциональность?
