# KidsMap UI Design

Этот skill определяет визуальные и UX-принципы KidsMap.az.

При работе с KidsMap используй его совместно с frontend-design.

# 1. Что такое KidsMap

KidsMap.az — каталог детских мест, секций, образовательных центров, развлечений и других активностей.

Основная задача интерфейса:

помочь родителю максимально быстро понять:

- что это за место;
- подходит ли оно ребёнку;
- где находится;
- какой возраст;
- сколько стоит;
- когда работает;
- как связаться;
- можно ли доверять информации.

UI должен уменьшать время поиска информации.

# 2. Характер бренда

Визуальное ощущение:

- семейный;
- дружелюбный;
- современный;
- чистый;
- живой;
- безопасный;
- понятный;
- немного игровой;
- но НЕ инфантильный.

KidsMap не должен выглядеть:
- как детский сад;
- как корпоративный SaaS;
- как государственный портал;
- как маркетплейс дешёвых товаров;
- как перегруженная рекламная площадка.

Целевая аудитория интерфейса — прежде всего родители.

# 3. Брендовые цвета

Основной зелёный:

#136F38

Светлые брендовые:

#CDE7C5
#A8D59B

Используй существующие CSS variables проекта, если эти цвета уже представлены через tokens.

Не размножай один и тот же цвет по CSS hardcode, если существует переменная.

# 4. Логотип и бренд

Основной знак KidsMap — зелёный медведь-геометка.

Не:
- перерисовывать;
- деформировать;
- менять пропорции;
- произвольно менять цвета;
- добавлять эффекты;
- заменять другим знаком

без прямого требования пользователя.

# 5. Главный UX-принцип

ИНФОРМАЦИЯ ВАЖНЕЕ ДЕКОРА.

Красивый интерфейс KidsMap — это интерфейс, где родителю легко найти нужную информацию.

Приоритет данных карточки места обычно:

1. Название / тип места.
2. Основная визуальная информация.
3. Возраст.
4. Цена.
5. Расписание.
6. Местоположение.
7. Контакты / CTA.
8. Описание.
9. Направления / услуги.
10. Отзывы и дополнительная информация.

Конкретный порядок может меняться в зависимости от страницы.

# 6. Progressive disclosure

Не показывай одновременно огромное количество вторичной информации.

Используй:
- раскрывающиеся блоки;
- "показать ещё";
- tabs;
- компактные состояния;
- modal/popover там, где это действительно облегчает интерфейс.

Но критически важные сведения нельзя прятать слишком глубоко.

# 7. Карточки мест

Карточку должно быть возможно быстро просканировать взглядом.

Не превращай её в набор десятков независимых рамок.

Используй:
- визуальные группы;
- whitespace;
- иконки;
- типографику;
- разделители

вместо постоянного добавления новых bordered containers.

Цена, возраст, расписание и контакты должны различаться визуально, но оставаться частью одной системы.

# 8. Расписание

Расписание особенно важно.

Оно должно позволять за несколько секунд понять:
- работает ли место сегодня;
- в какие дни работает;
- время;
- выходные;
- особый режим;
- занятия по записи / предварительной договорённости.

Дни недели должны иметь стабильное выравнивание.

Время должно иметь стабильное визуальное положение.

Не создавать хаотичные строки разной высоты без причины.

Группировать одинаковые дни/режимы, если это улучшает читаемость и не скрывает информацию.

Сегодняшний день можно аккуратно выделять.

Статусы:
- открыто;
- закрыто;
- круглосуточно;
- по записи;
- уточняется

должны различаться понятно, но не превращать блок в разноцветную таблицу.

# 9. Цены

Пользователь должен сразу понимать модель оплаты.

Поддерживать визуально разные случаи:
- бесплатно;
- фиксированная цена;
- от X;
- диапазон X–Y;
- несколько тарифов;
- бесплатный вход + платные услуги;
- цену необходимо уточнить;
- события с отдельными ценами.

Не показывай:
"от 50"
если цена фактически фиксированная 50.

Не выводи визуальное значение, которое противоречит backend source of truth.

# 10. Возраст

Возраст должен быть понятен без интерпретации.

Поддерживать:
- минимальный возраст;
- максимальный возраст;
- только нижнюю границу;
- все возраста;
- разные возрастные ограничения для разных услуг.

Не создавать UI, предполагающий обязательную верхнюю границу, если бизнес-логика её не требует.

# 11. Фильтры

Фильтр должен помогать быстро сузить каталог.

Главные принципы:
- понятные labels;
- видимое активное состояние;
- возможность быстро сбросить;
- минимум лишних controls;
- ясная связь filter → результат;
- mobile-friendly UI.

Не добавляй несколько разных способов управления одним и тем же параметром без необходимости.

# 12. CTA и контакты

Основные действия:
- позвонить;
- открыть Instagram/соцсеть;
- перейти на сайт;
- посмотреть местоположение;
- другие контакты.

Главные CTA должны быть заметными, но не конкурировать между собой чрезмерно.

Телефон может быть скрыт до действия пользователя, если такая логика предусмотрена системой.

Не изменять эту логику ради дизайна.

# 13. Отзывы

Отзывы должны выглядеть как пользовательский контент, а не как системная таблица.

Должны легко различаться:
- автор;
- дата;
- рейтинг;
- текст;
- ответ;
- действия;
- статус при необходимости.

Избегать лишних рамок вокруг каждого маленького элемента.

# 14. Локализация

KidsMap поддерживает:

AZ
RU
EN

Любой UI должен выдерживать различную длину текста.

Нельзя проектировать компонент только под одну конкретную строку.

Проверять:
- длинные названия;
- кнопки;
- labels;
- breadcrumbs;
- tabs;
- mobile.

Не решать проблему локализации уменьшением font-size до плохо читаемого значения.

# 15. Mobile-first

Большая часть взаимодействий каталога должна быть удобна пальцем.

Обязательно проверять около:

375px

Также:
768px
1024px
1440px

На мобильном:
- CTA доступны;
- фильтры удобны;
- текст читаем;
- карточки не перегружены;
- горизонтальный overflow отсутствует;
- sticky элементы не закрывают контент;
- dropdown/modal помещаются в viewport.

# 16. Визуальная система

Стремиться к единству:

- border-radius;
- spacing;
- typography;
- button heights;
- inputs;
- icons;
- borders;
- shadows;
- states.

Если в проекте уже существует design token — используй его.

Если обнаружено несколько почти одинаковых значений, сначала оцени возможность унификации.

Не проводить глобальный refactor design system без необходимости для текущей задачи.

# 17. Рамки и тени

KidsMap должен оставаться лёгким.

Не заключать всё в рамки.

Предпочтительный порядок разделения информации:

1. whitespace;
2. typography;
3. alignment;
4. background difference;
5. subtle divider;
6. border;
7. shadow.

Shadow использовать только если необходимо показать elevation.

# 18. Иконки

Иконки:
- простые;
- понятные;
- одного визуального семейства.

Не добавлять emoji вместо системных иконок.

Не смешивать несколько icon styles.

# 19. Декоративные элементы

Фирменный мир KidsMap может включать:
- карту;
- Mappy;
- железнодорожные/путевые мотивы;
- растения;
- небольшие детские/образовательные символы.

Но продуктовый интерфейс не должен становиться иллюстрацией.

Декор не должен мешать:
- чтению;
- поиску;
- фильтрации;
- карточке;
- CTA.

# 20. Админ-интерфейс

Админка имеет другой приоритет:

скорость и точность работы > декоративность.

Для админки:
- высокая информационная плотность допустима;
- формы должны быть логично сгруппированы;
- validation errors максимально понятны;
- зависимые поля визуально связаны;
- сложные редакторы должны иметь чёткую иерархию;
- actions должны быть предсказуемыми.

Не превращать административную форму в публичную маркетинговую страницу.

# 21. Сохранение бизнес-логики

Очень важное правило.

При визуальной работе сначала понять существующую логику.

Не изменять без необходимости:
- Django models;
- validation;
- readiness;
- API;
- permissions;
- тарифные режимы;
- schedule modes;
- обработчики JS;
- локализацию;
- backend source of truth.

Если UI кажется неправильным из-за данных, сначала выяснить, проблема визуальная или архитектурная.

# 22. Никаких вторых Source of Truth

Не дублировать backend правила на frontend вручную, если сервер уже передаёт необходимую конфигурацию.

Frontend должен отображать состояние, а не создавать конкурирующую бизнес-логику.

Перед добавлением нового условия найти существующий source of truth.

# 23. Процесс визуального изменения KidsMap

Для существенного UI-изменения:

1. Найти связанные template/CSS/JS.
2. Посмотреть существующую страницу.
3. Понять бизнес-состояния компонента.
4. Найти визуальные проблемы.
5. Определить минимальный набор необходимых изменений.
6. Реализовать.
7. Проверить в реальном браузере.
8. Проверить mobile.
9. Проверить AZ/RU/EN или минимум устойчивость к длинному тексту.
10. Проверить Console.
11. Убедиться, что функциональность сохранилась.

# 24. Chrome DevTools MCP

Если Chrome DevTools MCP доступен, обязательно использовать его для серьёзных визуальных задач.

Через него:
- открыть страницу;
- исследовать DOM;
- проверить computed CSS;
- посмотреть размеры;
- проверить Console;
- проверить Network при необходимости;
- проверить реальный итог.

Не пытайся полностью оценивать визуальный интерфейс только чтением CSS.

# 25. Как принимать дизайн-решения

Если пользователь дал screenshot/reference:

сначала определить, ЧТО в референсе является хорошим:
- композиция;
- spacing;
- hierarchy;
- component structure;
- typography;
- interaction.

Не копировать слепо внешность, если она конфликтует с KidsMap.

# 26. Финальный критерий

После изменения интерфейс KidsMap должен стать:

- понятнее;
- аккуратнее;
- быстрее для восприятия;
- визуально цельнее;
- удобнее на мобильном;
- согласованнее с остальным сайтом.

Если стало только "красивее", но сложнее пользоваться — задача выполнена плохо.
